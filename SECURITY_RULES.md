# SECURITY_RULES.md

## Security Rules

The NAQL project follows secure development practices for protecting application data, API credentials, and AI endpoints.

## 1. Never Expose Secrets

Sensitive credentials must never be exposed in:

- Client-side code
- Public repositories
- Screenshots
- Logs
- API responses

The OpenRouter API key must be used only on the server.

## 2. Never Hardcode API Keys

API keys must never be written directly inside source-code files.

Incorrect:

```ts
const apiKey = "sk-or-...";
```

Correct:

```ts
const apiKey = process.env.OPENROUTER_API_KEY;
```

## 3. Use Environment Variables

Sensitive configuration must be stored using environment variables.

Example:

```env
OPENROUTER_API_KEY=your_api_key
OPENROUTER_MODEL=openai/gpt-4o-mini
```

Local environment files such as `.env.local` must not be committed to Git.

## 4. Validate User Input

All user-controlled input must be validated before it is processed or forwarded to external services.

NAQL validates AI requests before calling OpenRouter. Invalid requests are rejected with controlled error responses.

## 5. Sanitize Untrusted Data

Data received from users or AI services must not automatically be trusted.

AI responses are parsed, checked, and sanitized before being returned to the application.

For example, service-provider IDs generated by the AI are checked against the actual list of valid provider IDs.

## 6. Protect Sensitive Information

Sensitive implementation details and credentials should not be returned to users.

Application errors should provide useful messages without exposing secrets or unnecessary internal information.

## 7. Keep AI Requests Server-Side

OpenRouter requests are performed from server-side Next.js API routes.

The browser communicates with the NAQL backend instead of communicating directly with OpenRouter. This prevents the API key from being exposed through browser developer tools.

## 8. Apply Rate Limiting

AI endpoints should be protected against excessive requests.

NAQL applies rate limiting before processing AI requests to reduce abuse and unnecessary API usage.

## 9. Handle External API Failures Safely

The application should safely handle:

- Missing API keys
- Invalid input
- Request timeouts
- Upstream API errors
- Invalid AI responses
- Rate-limit errors
- Unexpected server errors

## 10. Validate AI Output

AI-generated content must be treated as untrusted output.

Structured AI responses must be parsed and validated before use.

For service comparisons, returned provider IDs must match providers that already exist in the platform data.

## 11. Use Request Timeouts

External API requests should not remain open indefinitely.

NAQL uses an `AbortController` timeout for OpenRouter requests.

## 12. Do Not Log Secrets

Debugging logs must never print:

- API keys
- Authorization headers
- Environment secrets
- Sensitive user information

Logging safe API status information may be used when required for debugging.

## Security Checklist

Before deployment:

- [ ] `.env.local` is excluded from Git
- [ ] No API keys exist in source code
- [ ] No secrets are exposed to client components
- [ ] User input is validated
- [ ] AI responses are validated and sanitized
- [ ] AI routes use rate limiting
- [ ] External API requests use timeouts
- [ ] Error responses do not expose secrets
- [ ] Debug logs do not contain sensitive information
- [ ] OpenRouter requests remain server-side
